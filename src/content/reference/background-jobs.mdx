RsOpsHub runs three nightly jobs that sync content, generate notifications, and backfill work logs. Two scheduler modes are available, and only one is active at a time depending on the runtime environment.

## Scheduler modes

### In-process scheduler (self-hosted)

When `process.env.VERCEL` is falsy, `startCron()` registers three `node-cron` schedules inside the Next.js server process. No external worker, Redis instance, or separate scheduler is required. A `started` flag prevents duplicate registration during Next.js dev-mode hot reloads.

### Serverless endpoint (Vercel)

When the app runs on Vercel, the in-process scheduler stays off and `vercel.json` calls the `/api/cron` route instead. The route accepts `GET` or `POST`, requires `Authorization: Bearer <CRON_SECRET>`, and sets `maxDuration` to 300 seconds with an internal budget of 260 seconds so the response is always returned before the function is killed.

Query parameters:

| Parameter | Effect |
|---|---|
| `jobs` | Comma-separated subset of `content`, `notifications`, `worklog`. Defaults to all three. |
| `workspaceId` | Scope the run to a single workspace. Omit to process every workspace. |

Workspaces are processed in staleness order (oldest `*LastSyncAt` first), so a budget-truncated run still makes progress on the workspaces that need it most. Skipped workspaces are listed in the JSON response under `skipped`.

Example request:

```bash
curl -X POST "https://your-app.example.com/api/cron?jobs=content,worklog" \
  -H "Authorization: Bearer $CRON_SECRET"
```

## Schedules

All three jobs call `runNightly()` from `src/server/services/nightly.ts`. The in-process scheduler gives each run a 15-minute budget.

| Cron expression | Job key | Runs at (server local time) |
|---|---|---|
| `0 2 * * *` | `content` | 02:00 daily |
| `30 2 * * *` | `notifications` | 02:30 daily |
| `0 3 * * *` | `worklog` | 03:00 daily |

Cron expressions are evaluated in the server's local timezone. Set the `TZ` environment variable on your host to control when "02:00" falls in your wall clock.

## Job details

### content

Calls `syncAllContent(workspaceId)` for every non-deleted workspace. This runs three sub-syncs in sequence:

1. **Hacker News** syncs each workspace where `hnEnabled` is true and `hnUsername` is set. Walks the user's `submitted` list (up to 200 items per handle), fetches each item via the Firebase API, and upserts `ContentRecord` rows. Previously soft-deleted items are not resurrected. Updates `hnLastSyncAt` on success.
2. **Reddit** refreshes metrics on existing Reddit content records. Only the `comments` count is updated (RSS lacks other metrics). Updates `redditLastSyncAt` on success.
3. **dev.to** runs two passes: first pulls new articles newest-first (stopping at the first already-synced article), then refreshes metrics on existing records using the authenticated `/articles/me/all` endpoint when an API key is configured. Updates `devtoLastSyncAt` on success.

Each sub-sync has its own try/catch, so a failure in one platform does not block the others.

### notifications

Runs four steps per workspace, each isolated so one failure does not block the rest:

1. **Drive shared-doc offers** refreshes pending Google Drive shared-with-me documents.
2. **Sheets offers** refreshes pending Google Sheets shared-with-me documents.
3. **Linear sync** pulls teams, issues, notifications, and templates from Linear's GraphQL API.
4. **Workspace event scan** checks for overdue and due-soon tasks (within 24 hours) and missing integration connections, emitting `INTERNAL` or `SYSTEM` notifications.

### worklog

Calls `backfillWorkLogs(workspaceId, timezone)` for every workspace. By default this covers the previous 3 days. For each day, if a `WorkLog` row already has a non-empty summary (the owner wrote their own), the day is skipped. Otherwise the job counts completed tasks, created and published content, and closed Linear issues, then generates a summary. When `OPENAI_API_KEY` or `LITELLM_API_KEY` is set the summary uses an LLM; without either key it falls back to deterministic text.

## What is not on the cron

**Reddit** discovery of new posts is not automatic. New Reddit content enters the system only when the owner adds a handle or pastes a URL. However, once a Reddit content record exists, the nightly content job refreshes its comment count via the RSS feed (see the content job above).

**Linear** sync runs only on demand outside of the notifications job. Triggers include clicking Sync on the Linear integration card, refreshing the notifications page, and posting a comment from inside the app (which awaits a sync so the thread updates immediately).

## Switching to an external scheduler

The service functions that the cron calls are directly importable and callable from any queue worker. To migrate:

1. Stop the in-process scheduler by setting `process.env.VERCEL` to any truthy value, or by removing the `startCron()` call from your server entry.
2. Call the underlying functions from your preferred job runner (BullMQ, Inngest, or a plain cron trigger hitting `/api/cron`).

The key entry points are:

| Function | Module |
|---|---|
| `runNightly(opts)` | `src/server/services/nightly.ts` |
| `syncAllContent(workspaceId)` | `src/server/services/content-sync.ts` |
| `syncLinear(workspaceId)` | `src/server/services/linear-sync.ts` |
| `backfillWorkLogs(workspaceId, tz)` | `src/server/services/catchup.ts` |
| `scanWorkspaceEvents(workspaceSlug)` | `src/server/services/workspace-events.ts` |

All functions are idempotent. Re-running on failure is safe.

## Observability

Every job tick logs to stdout. Pipe stdout to your host's logging system (Datadog, Better Stack, CloudWatch) for a lightweight observability layer. The serverless `/api/cron` endpoint returns a JSON response with per-workspace results, errors, skipped workspaces, and total duration.
