---
title: Authentication
description: Two-principal auth model (owner and viewer), session cookie mechanics, rate limiting, CSRF protection, and stored credential encryption.
---

RsOpsHub uses two principals: **owner** (full read/write, defined by environment variables) and **viewer** (read-only, scoped to one workspace by an access code). There is no user table. Identity comes from `OWNER_EMAIL`/`OWNER_PASSWORD` for the owner, or a per-workspace 16-character access code for viewers.

## Owner login

`POST /api/auth/login` with a JSON body:

```json
{ "email": "owner@example.com", "password": "your-password" }
```

The route verifies credentials using constant-time scrypt comparison, adds a 250 ms artificial delay on every attempt, and returns `{"ok": true, "role": "OWNER"}` on success.

### Rate limiting and lockout

- **Rate limit**: 8 requests per minute per IP (sliding window).
- **Exponential lockout** per (email, IP) pair. After repeated failures, the delay between allowed attempts escalates through these steps: 0, 0, 5 s, 15 s, 1 min, 5 min, 15 min. A successful login clears the lockout.

On lockout, the endpoint returns HTTP 429 with a `Retry-After` header.

## Viewer login

`POST /api/auth/viewer` with a JSON body:

```json
{ "email": "viewer@example.com", "code": "a1b2c3d4e5f6a7b8" }
```

The code must be exactly 16 characters. It is matched against the workspace's stored access code. On success the response includes the workspace slug and name:

```json
{ "ok": true, "role": "VIEWER", "workspaceSlug": "my-ws", "workspaceName": "My Workspace" }
```

Each viewer login creates a `ViewerJoin` audit row (recording email, IP, user-agent, and the current `codeVersion`) and emits an internal notification to the workspace owner. The same rate-limit (8/min per IP) and exponential lockout scheme apply.

## Access codes

Each workspace has an access code: 16 lowercase hex characters generated from `randomBytes(8)`. The code is stored in plaintext and can be rotated from workspace settings. Rotating the code increments the workspace's `codeVersion`, which invalidates every active viewer session for that workspace.

## Session cookie

Both login flows set a cookie named `rs_session` with these attributes:

| Attribute | Value |
|---|---|
| `HttpOnly` | `true` |
| `Secure` | `true` in production |
| `SameSite` | `strict` |
| `Path` | `/` |
| `Max-Age` | 7 days (604 800 s) |

The cookie value is the session payload signed with HMAC-SHA256 (keyed by `SESSION_SECRET`) and then encrypted with AES-256-GCM (keyed by `TOKEN_ENC_KEY`). Rotating either key invalidates all sessions.

### Owner sessions

The payload includes a `fp` field, a SHA-256 fingerprint of the current `OWNER_PASSWORD`. On every request, the fingerprint in the cookie is compared against the live password hash. Changing `OWNER_PASSWORD` immediately invalidates all owner sessions.

### Viewer sessions

The payload includes the workspace ID (`wsId`) and the `codeVersion` at the time of login. On every request, the server checks that the workspace still exists, is not deleted, and that its current `codeVersion` matches the session value. Rotating the workspace access code invalidates all viewer sessions for that workspace.

## Logout

`POST /api/auth/logout` clears the `rs_session` cookie by setting `Max-Age` to 0.

## Authorization guards

Server-side code uses four guard functions to enforce access:

| Guard | Effect |
|---|---|
| `requireOwner()` | Requires a valid owner session. Used for all mutations. |
| `requireSession()` | Requires any valid session (owner or viewer). |
| `requireWorkspaceAccess(wsId)` | Owners always pass. Viewers pass only if their session is scoped to the given workspace. |
| `canViewWorkspace(wsId)` | Returns a boolean instead of throwing. Owners always return `true`. Viewers return `true` when they have a valid `ViewerJoin` for the workspace's current `codeVersion`. |

## CSRF protection

Mutating API routes call `requireSameOrigin()`, which checks the `Sec-Fetch-Site` header. Requests with a value other than `same-origin`, `same-site`, or `none` receive a 403 response. When `Sec-Fetch-Site` is absent, the `Origin` header is compared against the request host as a fallback. A mismatched origin produces a 403. A malformed origin produces a 400.

Next.js server actions have their own built-in CSRF protection, so this guard applies only to API route handlers.

## Stored credential encryption

Third-party tokens stored in the database (Linear API key, dev.to API key, PostHog API key, Cloudflare API token, and Google OAuth refresh token) are encrypted at rest with AES-256-GCM using the `TOKEN_ENC_KEY` environment variable.

The ciphertext format is `base64url(iv[12] || authTag[16] || ciphertext)`. Rotating `TOKEN_ENC_KEY` invalidates all stored tokens, requiring re-authentication with each integration.

## Rate limiter internals

The rate limiter is an in-memory sliding-window counter, scoped to a single server instance. It is not distributed across multiple instances. The bucket store evicts the oldest entries when it exceeds 10,000 keys. For production deployments behind multiple instances, this means each instance tracks limits independently.
